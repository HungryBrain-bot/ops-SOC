# 002. SOAR writer: Cortex XSOAR and Google SecOps SOAR, dry-run and test modes

## Status
Accepted (2026-11-24)

## Context
The investigation agent's result (summary, verdict, evidence with citations, recommended
next steps) must reach the SOC's case management. Two SOAR targets are supported:
Palo Alto Networks **Cortex XSOAR 8** and **Google SecOps SOAR**. No SOAR instance is
available, so the writer must be complete enough that connecting one needs credentials
only, and its requests must be exercised over real HTTP before then.

Vendor APIs (fetched 2026-11-24):

- **Cortex XSOAR 8.** Base URL `https://api-<fqdn>`; headers `Authorization: <API key>`
  and `x-xdr-auth-id: <API key ID>`.
  `POST /xsoar/public/v1/incident` creates an incident (`name` required; `type`,
  `severity` 0-4, `details`, `labels` [{type, value}], `createInvestigation`; 201 =
  created, 200 = blocked by a pre-processing rule)
  ([incidents API](https://cortex-docs.paloaltonetworks.com/xsoar-8-api/cortex-xsoar-8.x-apis/incidents)).
  `POST /xsoar/public/v1/entry` adds a Markdown War Room entry (`investigationId`,
  `data`; 412 = investigation closed)
  ([entry API](https://cortex-docs.paloaltonetworks.com/xsoar-8-api/cortex-xsoar-8.x-apis/entry)).
- **Google SecOps SOAR.** The v1 Chronicle API lists methods on
  `projects.locations.instances.cases` and has **no case-create method**: cases are
  created from alerts that SecOps ingests. Comments are added with
  `caseComments.create` on an existing case
  ([cases](https://docs.cloud.google.com/chronicle/docs/reference/rest/v1/projects.locations.instances.cases),
  [caseComments.create](https://docs.cloud.google.com/chronicle/docs/reference/rest/v1/projects.locations.instances.cases.caseComments/create)).
  The request line and body fields of `caseComments.create` were **not readable** through
  the fetch tool (the page body did not render). The URL used here follows Google's
  standard REST pattern for a `create` on a child collection and is unverified.

## Decision
1. **One `SoarWriter` interface**, like the connectors: `build_requests(case_report)`
   returns the exact HTTP requests (pure, no network), `send()` runs them through a
   swappable `Transport`. Two implementations:
   - **XSOAR**: create an incident labelled `ops-soc-case:<case id>`, severity mapped
     from the verdict, `details` = summary; then add one Markdown entry with the full
     report. `createInvestigation: true` so the entry has an investigation to land in.
   - **Google SecOps SOAR**: add one comment with the full report to the SecOps case
     that already holds the source alert. The case ID comes from configuration or the
     alert's mapping; the writer never creates a case (the API cannot).
2. **Three modes, dry-run by default.**
   - `dry-run`: write each request to `build/soar/<target>/<case id>.json`, auth headers
     redacted. No network.
   - `test`: send the same requests over real HTTP to a **local stub SOAR server**
     (`soar/stub_server.py`) that implements the endpoints above, checks method, path,
     auth headers and required body fields against our reading of the docs, stores what
     it receives and answers with documented status codes (201, 200, 412, 401). The
     test suite pushes every report through it end to end.
   - `live`: send to the real instance. Runs only when every credential env var for the
     target is set; otherwise fails with `MissingCredentials`.
3. **What the writer never does**: change incident status, severity after creation,
   owner, or close anything; run playbooks other than the one the incident type starts.
4. **Content** is Markdown generated by the `writing` model tier (ADR 001) from the case
   record; evidence IDs and query text are included so an analyst can rerun them.
5. **Idempotency**: XSOAR incidents carry the case ID label, and a resend is refused by
   the writer if a local record shows the case was already written to that target.
   Searching XSOAR for the label before creating is not implemented (search API not
   checked).

## Alternatives considered
- **Comments on Defender / Sentinel incidents via Graph.** No extra product, but keeps
  results out of the SOAR where analysts work cases.
- **Mock transport only (no HTTP).** Enough to check request shape, but never exercises
  serialisation, headers and status handling over a socket. The stub server does.
- **Vendor SDKs (`demisto-py`, Google client libraries).** Hide the requests; two
  dependency trees for three calls.

## Consequences
- `test` mode proves the writer sends what our reading of the docs says, over HTTP,
  and handles the documented responses. It does not prove a real XSOAR or SecOps
  instance accepts it: "not verified" until a logged live call.
- Google SecOps SOAR depends on the source alert being ingested into SecOps first;
  without a case ID, the writer reports "no case to write to" and stops.
- The `caseComments.create` body field names are unverified (see Context); check them
  against the rendered reference before the first live call.
